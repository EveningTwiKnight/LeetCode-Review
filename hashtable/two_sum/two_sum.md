# 1. 两数之和

**难度**：**Easy**

**标签**：`array` 、`hash-table`

**日期**：2026/07/19



### 题目描述

​	给定一个整数数组 `nums` 和一个整数目标值 `target`，请你在该数组中找出 **和为目标值** *target*  的那 **两个** 整数，并返回它们的数组下标。

​	你可以假设每种输入只会对应一个答案，并且你不能使用两次相同的元素。

​	你可以按任意顺序返回答案。

### 我的思路

​	很容易想到的就是利用枚举法遍历完全整个数组，通过两次for循环并且验证是否满足*target*，最终得出两个元素下标，所以对于枚举法的详细过程内容不再过多赘述。

### 正确思路

​	首先根据题目意思，每种输入只需要对应一个答案的话，在遇到输出结果的时候立刻就停下并返回两个元素对应的下表就可以了，并不需要彻底的遍历完全整个数组找出所有答案，这是最容易想到的优化。

​	其次，在枚举过程中，注意到很多元素其实是被反复的取出的，如果可以减少重复取出同一个元素的次数，那么就可以实现下降时间复杂度的问题了。

![枚举法优化方向](D:\gits\leetcode-review\hashtable\two_sum\枚举法优化方向.svg)

​	既然如此，减少反复读取的次数就是优化的主要方向，具体怎么解决呢？

​	那就先让每个数组元素只读取一遍，也就是只用一个for循环来遍历这个数组，这种情况下，我们手头上只有当前正在被读取的元素的值，肯定是不足够解决题目的要求的。我们至少还需要一个数才能解决问题。

​	在读取第一个数的时候，一定是无法得出答案的，因为此时我们只知道一个元素的值，所以在这次循环中我们会继续往后读取，既然我们已经不能反复读取同一个元素了，在我们不追加任何额外的变量的情况下，第一个元素就会被我们抛弃，我们可能会就此错过某个正确答案。所以我们先存下第一个元素。

​	第二个元素之后，我们有了第一个元素，两个元素加起来看看是否和**target**一致，如果一致现在就可以结束了，不过大部分情况没有这么巧合。假设现在两者和不一致，我们就要向后继续寻找答案。第一个元素我们现在已经有了，如果抛弃第二个元素，那么我们也会有可能错过正确答案，所以我们存下第二个元素。

​	一样的，我们重复上述操作N次之后，遍历完成了整个数组，我们也存下了整个数组的元素。我们再思考一下这个过程。我们先假设目前的情况是根本不存在两个元素加起来等于**target**的情况，也就是最差情况。

​	我们整体干了什么，我们存下的这些数据，其实就是我们之前遍历过的元素。我们只是因为当时不想浪费和担心漏掉正确答案而存储下来了。我们把这些数据先看成是一个数组，我现在先命名这个数组为**Readed[]**

​	**Readed[]**存储了过去我们遍历后得到的元素，那么我们是如何判断我们是否还要继续往后走的呢？假如我们的**Readed[]**数组里面已经存放了***i-1***个元素，我们现在正处在第i个元素，那么我们只需要一个个看**Readed[]**里面有没有和第***i***个元素相加等于**target**的元素。现在依然考虑最差情况，也就是没有找到的情况，遍历完成我们**a[]**数组里的每个元素后，各自都要读取这个**Readed[]**数组i-1次。我们现在针对最多的比对次数求一次和。

$$
\sum_{i=1}^{n} (i-1) = 0 + 1 + 2 + \cdots + (n-1) = \frac{n(n-1)}{2} = \frac{n^2 - n}{2}
$$

​	现在比起最早暴力枚举的$n^2$次比对次数来讲，至少减少了$n/2$次比对次数，尽管时间复杂度暂时还没有根本的变化，我们仍然还是实现了一部分的优化。我们已经尽可能减少了重复比对的次数，为什么时间复杂度仍然还是$O(N^2)$呢？

​	其实答案非常明显，我们运用**Readed[]**数组本质其实还是类似于前面反复读取的操作，我们其实只是想寻找某个元素值等于**target-a[i]**的元素，但是在**Readed[]**数组里面我们不得不从头到尾的遍历一遍，这也导致了比对次数并没有什么太大的变化，只是把比对过程从**a[]**数组里转移到了**Readed[]**数组里。

​	既然现在的优化思路本身并不是什么太大的问题，如果我们能让Readed[]数组查询是否含有某个元素值的速度变快，就可以实现最开始我们预期的时间复杂度$O(N)$了。自带的数组这个数据结构就行不通了，还有什么其他数据结构吗？

​	我们现在就好像把东西全都存放在了一个有很多抽屉的柜子里面，我们并不能看见柜子里面到底放着的是什么，所以我们要是想找某件物品，就只能一个一个抽屉去翻。如果我们在每个抽屉外面用便利贴贴上一个标签，我们是不是就可以一下子看见到底是哪个抽屉存放了我们需要的物品了？现在我们Readed[]数组也是类似的情况，它现在是一个没有任何标记的柜子，里面有好多抽屉，我们只能一个一个翻去寻找我们需要的那个元素值。假如我们给每一个数组元素贴一个元素值的标签，我们就可以直接找到这个元素到底在哪里了。

​	那么很自然的一个想法，既然我们要找的是元素值，我们直接把数组下标当成元素值来看待怎么样？**Readed[12]**我就存放在**a[]**数组里**12**出现的位置，**Readed[3]**我就存放**a[]**数组里面**3**出现的位置。我们现在思考一下它的时间复杂度。我假设我要寻找元素***k***，因为是直接直接读取**Readed[k]**，所以我们只需要$O(1)$的时间就可以找到***k***在哪里以及***k***是否存在（只要看这个Readed[k]是不是空的就可以了）。

​	很好，这直接就解决了我们之前最头疼的问题，我们现在不需要再遍历**Readed[]**数组来寻找我们需要的那个元素值了，但是带来了两个新问题。

​	**1.如果k的值非常的大，我们的Readed[]数组就要很长，那么它占据的内存空间可能会严重超出我们计算机的内存上限导致无法运行。**

​	**2.如果我们有一个元素值，在不同地方出现了两次，我们怎么办。**

​	我们先来解决第二个问题吧，想在一个抽屉里存放多个元素，最直接的想法就是，我再嵌套一个数组不就好了。这个办法没办法实行，因为你根本不知道有多少个重复元素，内部的数组你都没有办法声明他的长度。那么就只剩下另一个办法了，就是用**链表**。我们让**Readed[]**数组每个元素存放一个链表， 把对应元素的下标变成一个节点接在那个链表头上就解决这个问题了。

​	然后是第一个问题，假如元素值很大，不如我们就让每个元素值和10取模吧，这样我们的数组只需要0-9这十个空间就可以解决这个问题了。对于同一个下标对应的两个不同的元素值，我们可以采用和刚才解决第二个问题一样的方法来应对，也就是还是用链表的思路解决这个问题，这里就不再重复赘述了。

​	刚才我们所作的对10取模的操作也可以变成其他的运算操作，这个将**“原始数据”**映射为**“数组下标”**的数学运算的运算并不唯一。我们刚才的这个数学运算的名字叫**哈希函数（Hash Function）**。我们的这个**Readed[]**数组，经过我们刚才一系列的优化操作，现在可以正式称其为**哈希表（HashMap）**.

​	![Hashmap的大致数据结构](D:\gits\leetcode-review\hashtable\two_sum\Hashmap的大致数据结构.svg)



### 正解代码

在 Java中，我们不需要自己手写哈希表的数据结构。Java 标准库已经提供了现成的 **HashMap** 类，我们直接拿来用即可。下面给出 Java 的参考正解代码。

```Java
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> hashtable = new HashMap<Integer, Integer>();	//新建哈希表
        for (int i = 0; i < nums.length; ++i) {			
            if (hashtable.containsKey(target - nums[i])) {	 		 //如果找到了，就获取下标
                return new int[]{hashtable.get(target - nums[i]), i}; //并且返回当前的下标
            }
            hashtable.put(nums[i], i);	//没找到就把现在的元素放进哈希表
        }
        return new int[0]; 				//找不到答案，就返回一个空数组
    }
}
```




## 复杂度分析

**我的思路**：时间复杂度：$O(N^2)$、空间复杂度：$O(1)$

**正解**：时间复杂度：$O(N)$、空间复杂度：$O(N)$

## 总结

​	在**“判断某个元素是否存在”**、**“统计某个元素出现的次数”**或者**“根据一个值直接查找它对应的信息”**这类需求，哈希表几乎都是首选。当然还有很多关于哈希表的一些进阶用法，在未来其他相关的题目中我们可以再深入讲讲。
